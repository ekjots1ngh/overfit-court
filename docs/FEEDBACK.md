# Feedback on Nebius Token Factory, Sandboxes and NVIDIA tools

The three things that cost the most time, with a severity:

1. Blocker: contree-sdk sends the names of unset environment variables as the credentials themselves, so a missing NEBIUS_PROJECT_ID fails only at the server, as a bare authentication error (Sandboxes item 2).
2. Friction: what a Nemotron 3 model accepts (the thinking switch, JSON mode) and where its reasoning arrives are found by trial and error, not from the API (Token Factory items 1, 3 and 8).
3. Friction: Sandboxes is two products on paper (ConTree and Token Factory Sandboxes), and the results path (truncation, exit codes, time limits, image cleanup) is under-documented, so the executor was written from the SDK source (Sandboxes items 1, 3, 5, 6 and 7).

Every item says where it comes from: "seen in the console", "read in the SDK source", "expected, not yet observed" (from the docs and model cards, written before the first live call), or "live" once the live run has confirmed or contradicted it. Each item says what happened, why it mattered, and a suggested fix.

## Token Factory and Nemotron 3

1. Turning thinking off isn't an API parameter. (Read in the docs; expected, to confirm live.) Nemotron 3 thinks before it answers by default. That is right for planning and writing code, and wasteful for a two-line audit or triaging search results. The switch is the chat template's enable_thinking, which the OpenAI SDK has no field for, so it has to go in extra_body as chat_template_kwargs, and whether a given model accepts it is found out by trying. The client sends it, and if the request is rejected, retries without it and remembers for the rest of the process. Suggestion: accept the OpenAI-style reasoning_effort (or a documented thinking flag) on every reasoning model and map it to the template, and say on each model card whether it is supported.

2. Thinking spends the answer's budget. (Expected, to confirm live.) With thinking on, a max_tokens that would be generous for the answer alone can run out mid-thought: the reply is empty and finish_reason is "length". A careful client retries with more room; a quick script just sees nothing. Suggestion: recommended budgets per model on the model card, or a separate limit for reasoning tokens, so the answer's budget can't be eaten.

3. Capabilities are discovered by trial and error. (Read in the catalogue; expected, to confirm live.) JSON mode is supported by some models and not others (the catalogue's "JSON mode" tag). Combined with item 1, a rejected request has two possible causes, so the client retries without each optional part in turn to learn which one the model refused. Suggestion: list each model's capabilities (JSON mode, JSON schema, the thinking switch, context length) in the /v1/models response, so a client can decide before sending.

4. Model ids are long, and the three Nemotron 3 tiers spell theirs three ways. (Seen in the console.) The catalogue's public endpoints are nvidia/nemotron-3-super-120b-a12b (lower case), nvidia/Nemotron-3-Ultra-550b-a55b (capitalised) and nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B (capitals, and "NVIDIA" twice). Guessing Nano's id from Super's gives one that doesn't exist, which is the mistake this project's own defaults first made. The client now matches the configured id against the account's model list ignoring case, the organisation and a repeated "NVIDIA-", and the pre-flight check lists the Nemotron ids the account can use. Suggestion: stable aliases (nemotron-3-super-latest), and an error for an unknown model that suggests the nearest id.

5. Sampling advice lives in the model cards, not in the catalogue. (Read in the model cards.) NVIDIA's Nemotron 3 cards recommend temperature 1.0 and top_p 0.95 for Super and Ultra, and 1.0 and 1.0 for Nano, when reasoning is on; a client that keeps the usual low temperature for "deterministic" tasks gets worse reasoning. This project follows the cards for its thinking roles; its auditor and clerk run with thinking off at temperature 0.2, which is our own choice for steady JSON, not NVIDIA's advice. Suggestion: show the recommended sampling settings next to each model in the Token Factory catalogue and playground, since that is where people copy their first request from.

6. Spend has to be computed client-side. (Read in the docs; expected, to confirm live.) Responses report tokens, not cost, so per-trial cost accounting needs per-model prices copied into configuration by hand (PRICE_* in .env.example), and a public app's spend cap is only as right as those copies. Suggestion: return the cost of each request in usage, or prices in the model list.

7. The playground's code uses a regional address the docs warn against. (Seen in the console.) "View code" for Nemotron 3 Super gives base_url https://api.tokenfactory.us-central1.nebius.com/v1/, and for Nano eu-north1, because that is where each runs today. The docs' page on public endpoints says a base_url that includes a region can stop working when the processing region changes, and the API reference gives the global https://api.tokenfactory.nebius.com/v1/. Copy Super's snippet, switch the model to Nano, and the request may go to a region that doesn't serve it. This project uses the global address. Suggestion: show the global base_url in the playground's code for public endpoints.

8. Where the reasoning arrives, and the empty-content case. (Expected, to confirm live.) NVIDIA's own Nemotron 3 examples read the model's thinking from a separate reasoning_content field, while other servers put it inline in think tags, and a server with a reasoning parser can return an empty content with the whole answer sitting in reasoning_content and finish_reason "stop". A client that only reads content sees an empty reply and pays for a retry it didn't need. The Super model card suggests the chat template flag force_nonempty_content for coding agents, which by its name is aimed at exactly this. The client now reads both fields, salvages an answer from the reasoning before any retry, sends force_nonempty_content with enable_thinking, and logs reasoning tokens from completion_tokens_details when they are present. Suggestion: document, per model, where reasoning arrives and whether usage counts reasoning tokens, and make force_nonempty_content the default when JSON mode is requested.

## Token Factory Sandboxes and contree-sdk

1. Two names and two endpoints for one product. (Read in the SDK source.) The SDK and MCP server call the product ConTree and default to contree.dev, while the hackathon and the Token Factory docs call it Sandboxes at api.tokenfactory.nebius.com/sandboxes. I had to read the SDK source (ContreeEndpoint.TOKEN_FACTORY_SANDBOXES, the IAMAuth defaults) to be sure which endpoint and auth scheme applies. Suggestion: one quickstart page for Token Factory users that states the endpoint, the auth headers and the SDK constructor near the top.

2. Unset credentials are sent as literal strings. (Read in the SDK source and reproduced offline against contree-sdk 0.3.6.) IAMAuth's fields hold either a value or the name of the environment variable to load it from, and Auth.resolve() keeps the default when the variable is missing. So with NEBIUS_API_KEY and NEBIUS_PROJECT_ID unset, IAMAuth().resolve().get_headers() returns Authorization "Bearer NEBIUS_API_KEY" and Project "NEBIUS_PROJECT_ID": the SDK sends the variable names as the token and the project, and the failure only comes back from the server as an authentication error that says nothing about why. Three-line repro: unset both variables, then from contree_sdk.auth import IAMAuth; print(IAMAuth().resolve().get_headers()). This project now checks the credentials once (a whoami call) before uploading anything and names the two variables in its error. Suggestion: raise when the client is built if a field still holds its own environment-variable name, with a message that says where to find the project ID and that Sandboxes access must be enabled for that project.

3. Output truncation is silent unless you know to check. (Read in the SDK source; expected, to confirm live.) default_truncate_output_at is 65,535 bytes, so returning results on stdout breaks for anything beyond a small payload. ContreeResult.truncated does exist, but nothing warns or raises when it is true, so a truncated result is easy to parse as a short one. Reading a file back from the resulting image works well, but only with disposable=False. Suggestion: document "write a file, keep the image, read it back" as the standard way to return data, and log a warning when output was truncated.

4. Pinning the environment is up to you. (Expected, to confirm live.) A sandbox built from python:3.12-slim with a bare pip install numpy pandas gets whatever versions are current that day, so the same job can give different numbers in a sandbox and on the machine that launched it. I now install the launching machine's exact versions and cache the image per version set. Suggestion: a documented pattern (or a helper) for building an image from a requirements file and reusing it by content hash.

5. There is no image delete in the SDK. (Read in the SDK source.) Results can only be read back from a run kept with disposable=False, and the SDK exposes tag and untag but no delete. So every branch leaves an image behind: about nine per executor run (the dependencies image, the checkpoint and eight branches), twenty or more per trial with its evidence room, and a public app keeps accumulating them. Suggestion: a delete (or an expiry on untagged images), and a line in the docs on what kept images cost.

6. Queued time counts against the time limit, as far as the SDK shows. (Expected, to confirm live.) The SDK starts its clock when the operation is created and raises OperationTimedOutError once the run's timeout has passed, so a run that waits in a queue arrives at its code with less of its limit left, and the docs don't say whether the service's own instance timeout starts at submission or at process start. A run the service stops at its limit is reported in the process state (timed_out), which this project uses to send the code back to the engineer instead of counting a lost branch. Suggestion: say in the docs when each clock starts, and expose queue time in the result's resources.

7. Exit-code semantics are undocumented. (Expected, to confirm live.) Does a failing command come back as a successful operation with a non-zero exit_code, or as a failed operation (FailedOperationError)? A repair loop depends on the answer: in the first case the crash goes back to the model with its traceback, in the second it looks like infrastructure. This project handles both, and its pre-flight now runs one deliberately failing job (python -c "import sys; sys.exit(3)") to find out which it is. Suggestion: one sentence in the run() docstring, and a worked example of a non-zero exit.

8. Small SDK nits. (Read in the SDK source.) ContreeResult exposes elapsed_time while the image object exposes the same value as elapsed, so the first attribute I wrote failed; one name, or an alias, would do.

## What went well

One OpenAI-compatible endpoint for all three Nemotron 3 tiers made role-based routing trivial: the planner, engineer, auditor, clerk and judge are the same client with a different model id and thinking setting, so moving a role between Nano, Super and Ultra is a one-word change, and examples/tier_experiment.py can compare them directly on the same leaks. The checkpoint-and-branch model is exactly right for experiment grids: setup runs once, every branch is isolated, and each result carries its own compute time and cost, so per-trial cost accounting is a few lines of code. It also enabled something I haven't seen pitched before: using isolation as a scientific guarantee, because the research checkpoint physically doesn't contain the held-out data. And the console's Sandboxes page has a small shell (contree images lists the shared images, contree use python:3.12-slim picks one, and every command after that runs in a sandbox and leaves a new image) that confirmed, in two minutes with no code and no API key, that python:3.12-slim is already imported and that sandboxes can reach PyPI; link it from the SDK quickstart as the way to check an image or network access before writing code.
